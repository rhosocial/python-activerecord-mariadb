## Quick Start

```python
from typing import ClassVar, Optional

from rhosocial.activerecord.base import FieldProxy
from rhosocial.activerecord.backend.impl.mariadb.backend import MariaDBBackend
from rhosocial.activerecord.backend.impl.mariadb.config import MariaDBConnectionConfig
from rhosocial.activerecord.backend.expression import CreateTableExpression
from rhosocial.activerecord.backend.expression.statements import (
    ColumnConstraint,
    ColumnConstraintType,
    ColumnDefinition,
)
from rhosocial.activerecord.backend.expression.types import IntegerType, VarCharType
from rhosocial.activerecord.model import ActiveRecord


class User(ActiveRecord):
    __table_name__ = "users"

    id: Optional[int] = None
    name: str
    email: str

    c: ClassVar[FieldProxy] = FieldProxy()


User.configure(
    MariaDBConnectionConfig(
        host="localhost",
        port=3306,
        database="myapp",
        username="user",
        password="password",
    ),
    MariaDBBackend,
)

dialect = User.__backend__.dialect
User.__backend__.execute(*CreateTableExpression(
    dialect,
    "users",
    columns=[
        ColumnDefinition(
            dialect, "id", IntegerType(dialect),
            constraints=[ColumnConstraint(dialect, ColumnConstraintType.PRIMARY_KEY,
                is_auto_increment=True)],
        ),
        ColumnDefinition(dialect, "name", VarCharType(dialect, 100)),
        ColumnDefinition(dialect, "email", VarCharType(dialect, 255)),
    ],
).to_sql())

user = User(name="Alice", email="alice@example.com")
user.save()
rows = User.query().where(User.c.email == "alice@example.com").all()
```

### Async

`AsyncMariaDBBackend` exposes the same API. Method names are identical; add
`await`.

```python
from rhosocial.activerecord.backend.impl.mariadb.backend import AsyncMariaDBBackend
from rhosocial.activerecord.model import AsyncActiveRecord


class User(AsyncActiveRecord):
    ...


User.configure(config, AsyncMariaDBBackend)
rows = await User.query().where(User.c.email == "alice@example.com").all()
```

## MariaDB-Specific Features

### Full-text search

```python
Article.query().where(
    "MATCH(title, content) AGAINST(? IN BOOLEAN MODE)",
    ("+python -java",),
).all()
```

### System-versioned tables

Query historical rows with `FOR SYSTEM_TIME`. This requires the table to be
declared `WITH SYSTEM VERSIONING`; the backend does not add it implicitly.

```python
User.query().where(
    "id = ? FOR SYSTEM_TIME BETWEEN ? AND ?",
    (1, "2026-01-01", "2026-06-30"),
).all()
```

### JSON operators

`->` and `->>` are always rendered as `JSON_EXTRACT(...)` and
`JSON_UNQUOTE(JSON_EXTRACT(...))`. Those behave identically on every
supported release, so one statement produces one result everywhere.
MariaDB 13.1 added a native `column -> path` form, but it applies only to a
real JSON *column* — `CAST(x AS JSON) -> '$'` is a syntax error even on
13.1 — so it is not used as the general rendering.
`supports_json_arrow_operators_native()` reports whether it is available.

## Version Gates

Gates below are the versions at which this backend's own `supports_*`
switch returns `True`, probed at 10.1.3, 10.2, 10.2.1, 10.2.3, 10.2.7, 10.3, 10.4, 10.5, 10.6, 11, 11.4, 11.8, 12, 12.3, 13, 13.1.
A version is the first probe at or above the real gate, so each is an
upper bound within one ladder step. Switches already `True` at the
oldest release carry no gate and are omitted.

| Min version | Capabilities that turn on |
|---|---|
| 10.2 | `basic_cte`, `filter_clause`, `grant_if_exists`, `grant_or_replace`, `read_only_transaction`, `recursive_cte`, `transaction_mode`, `window_frame_clause`, `window_functions` |
| 10.2.1 | `check_constraint` |
| 10.2.3 | `geojson`, `json_merge_patch`, `json_type`, `trigger_order` |
| 10.3 | `alter_sequence`, `alter_table_wait`, `constraint_enforced`, `create_sequence`, `drop_sequence`, `except`, `for_update_nowait`, `for_update_skip_locked`, `intersect`, `rename_table_wait`, `sequence`, `system_versioning`, `temporal_tables`, `truncate_wait` |
| 10.4 | `instead_of_trigger`, `multiple_triggers_per_timing` |
| 10.5 | `alter_table_if_exists`, `analyze_table_persistent`, `rename_table_if_exists`, `returning`, `returning_delete`, `returning_expression`, `returning_for_delete`, `returning_for_insert`, `returning_for_replace`, `returning_insert` |
| 10.6 | `explain_analyze`, `json_table`, `rename_index` |
| 13 | `returning_for_update`, `returning_update` |

### Supported versions policy

| Line | Status | Rationale |
|------|--------|-----------|
| **12.3** | **Recommended baseline** | LTS, maintained to June 2029 |
| 13.0 | Supported, opt-in | GA, rolling, non-LTS |
| 13.1 | Not recommended for production | Release candidate; `utf8` alias change and `mariadb-dump` behaviour need independent validation |
| 11.8 | Supported | Previous LTS |
| 10.2 – 11.7 | Supported | Older lines, CI-covered |

There is no upper bound: the backend does not reject a version it has not
seen. Feature gates resolve to *enabled* when the server is newer than a
feature's introduction version, so **new syntax is assumed available**; if
that assumption is wrong the server rejects the statement. Removals are
handled per feature — `supports_function_name("des_encrypt")` returns
`False` on 13.0+, where the function was removed.

### The `utf8` character set alias

`utf8` is a server-side alias whose meaning changed in MariaDB 13.1
(MDEV-30041): it resolved to `utf8mb3` up to 13.0 and to `utf8mb4` from
13.1, because `old_mode` no longer sets `UTF8_IS_UTF8MB3` by default.

```sql
CREATE TABLE t (s VARCHAR(50)) CHARACTER SET utf8
-- MariaDB <= 13.0  ->  utf8mb3_uca1400_ai_ci   (4-byte characters rejected)
-- MariaDB >= 13.1  ->  utf8mb4_uca1400_ai_ci   (4-byte characters accepted)
```

This backend resolves the alias to **`utf8mb3`** — the meaning it always had
before 13.1 — before emitting it, so one DDL statement produces one schema
on every supported server. Ask for `utf8mb4` explicitly if you want 4-byte
storage. This affects DDL only: `SET NAMES utf8` already resolved to
`utf8mb4` on every version tested, including 12.2.

### Reserved words

Identifiers are quoted by default, and the reserved-word check is
version-aware, because MariaDB adds reserved words in otherwise-minor
releases — `conversion` and `to_date` became reserved in **12.3**, and
`deny` in **13.1**. An unquoted identifier matching a reserved word emits an
`IdentifierQuotingWarning`. It is a warning, not an error, so passing
`need_quote=False` remains possible at your own risk.

## Known Limitations

- **No connection pooling.** `pool_size` and friends are accepted by the
  config class but not consumed by the backend; `connect()` opens one
  persistent connection.
- **`RETURNING` on `UPDATE` needs 13.0+.** `INSERT`/`DELETE`/`REPLACE` get it
  at 10.5.
- Schema-level objects are unsupported: `create_schema`, `drop_schema`,
  `attach_partition`, `detach_partition`, and `deferrable_*`. There is no
  `QUALIFY`, `WITHIN GROUP`, `LATERAL VIEW` or `VECTOR` type support.
- `IS JSON` and `TO_DATE()` are not implemented. `MARIADB_VERSION_BOUNDARIES`
  carries constants for them, but no `supports_*` switch consumes them, so
  nothing gates or renders them yet.

## Testing

Tests require a reachable MariaDB server and must run serially.

```bash
export PYTHONPATH=src:tests
.venv3.14-ubuntu26.04/bin/pytest tests/
```

The shared contract suite lives in
[python-activerecord-testsuite](https://github.com/rhosocial/python-activerecord-testsuite):

```bash
PYTHONPATH=tests .venv3.14-ubuntu26.04/bin/pytest \
  ../python-activerecord-testsuite/src/rhosocial/activerecord/testsuite/feature/
```
