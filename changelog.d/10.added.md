The MariaDB dialect now answers the column-type protocol. `MariaDBColumnTypeMixin` (`mixins/column_type.py`), derived from core's `ColumnTypeMixin` and composed into `MariaDBDialect` ahead of every core fallback, carries the complete 18-entry table (`suggested_column_types()`), so which column class a common Python type means on MariaDB is this backend's own answer rather than a portable default. All five containers -- `dict`, `list`, `tuple`, `set` and `frozenset` -- answer `JSONColumn`, because MariaDB implements no array type at all, while `float`, `decimal.Decimal` and `datetime.timedelta` answer `NumericColumn`, the exactness a `DECIMAL` carries being a value-layer and DataType distinction rather than an operation surface. Below 10.2 there is no JSON function family at all, where `dict` answers `None` -- the protocol's last resort -- so resolution fails at model definition and points at `UseColumnType` instead of rendering SQL the server rejects; the four containers keep their `JSONColumn` answer below that gate, because length and containment over JSON text survive where the path-access family does not. `uuid.UUID` is `UUIDColumn` on every version, including those below 10.7 where MariaDB has no native `UUID` type -- the native type is a storage fact and does not change what a UUID value can do, so gating the answer on it would flip the column class for a storage reason, which is the exact confusion the two-layer split exists to prevent. The per-operation narrowing that used to travel with the table (`ilike` on a string, `unnest` / `json_table` / `json_equal` on JSON) is not part of the protocol, and each of those facts is already owned by a probe that answers it: `supports_ilike()`, `supports_json_table()` and the JSON mixin's own version gates.

`TrimMixin`, `LpadMixin`, `RepeatMixin` and `RpadMixin` are composed into the dialect for core's new `trim` / `lpad` / `rpad` / `repeat` nodes, with no override: MariaDB spells all four natively -- `TRIM([BOTH|LEADING|TRAILING] [chars] FROM str)`, `LPAD`/`RPAD(str, len, padstr)` and `REPEAT(str, n)` -- so the shared default renderers are the answer here. `MariaDBTypeSupport` is no longer declared and then shelved: it is exported from `protocols/__init__.py`, composed into `MariaDBDialect` and listed in the conformance surfaces, which makes all nine of its `supports_mariadb_*` members reachable for the first time, and `UUIDType` leaves the list of types this backend cannot render, because `format_data_type_uuid` does exist and version-gates on 10.7.

Introspection now populates `IntrospectionColumnInfo.parsed_data_type` through `DataType.parse_data_type_str`, which MariaDB was the only backend not to do, so the schema differ compares type *values* rather than the base word alone -- `VARCHAR(100)` vs `VARCHAR(200)`, an `ENUM`'s labels and `INT` vs `INT UNSIGNED` are all differences the differ now sees, where before the whole type-identity model was inert on this backend. An unreadable catalog string degrades that one column to the string comparison with a `RuntimeWarning` rather than aborting `list_columns` for the whole table, because the catalog is not under this backend's control. A spatial column's declared reference system, which MariaDB keeps only in `information_schema.GEOMETRY_COLUMNS.SRID` and never writes into `COLUMN_TYPE` or `SHOW CREATE`, is folded back into the type text by a left join, so the parsed type is the declared one and a reference-system change is visible to the differ.
