Add `ALTER TABLE ... EXCHANGE PARTITION` support to the MariaDB backend. `MariaDBExchangePartitionExpression` (`expression/partition.py`, re-exported from the backend's `expression` package) names the partitioned table, the partition and the exchanging table, and `format_exchange_partition_statement` renders the statement; the validation clause carries one parameter per spelling (`with_validation` / `without_validation`), setting both raises `ValueError` at construction, a non-`Table` argument in either table slot raises `TypeError`, and leaving both unset renders no clause. The validation options are gated by the measured `MARIADB_VERSION_BOUNDARIES['EXCHANGE_PARTITION_VALIDATION']` boundary of 11.4.0: `WITH VALIDATION` and `WITHOUT VALIDATION` are refused by name below it and rendered from it, while the bare form stays available from 10.2, and `WITHOUT VALIDATION` is honored on the server rather than parsed-and-ignored. The `supports_exchange_partition`, `supports_exchange_partition_with_validation` and `supports_exchange_partition_without_validation` probes are declared on the `MariaDBPartitionSupport` protocol.

The MariaDB dialect now answers the column-type protocol: `MariaDBColumnTypeMixin` (`mixins/column_type.py`, composed into the dialect ahead of core's `ColumnTypeMixin`) carries the complete 18-entry table (`suggested_column_types()`), so which column class a common Python type means on MariaDB is this backend's own answer rather than a core default. `dict`, `list`, `tuple`, `set` and `frozenset` are all `JSONColumn` — MariaDB implements no array type — while `float`, `decimal.Decimal` and `datetime.timedelta` answer `NumericColumn`, the exactness a `DECIMAL` carries being a value-layer and DataType distinction rather than an operation surface. Below 10.2 there is no JSON function family at all, where `dict` answers `None` — the protocol's last resort — so that resolution fails at model definition and points at `UseColumnType` instead of rendering SQL the server rejects; the four containers keep their `JSONColumn` answer below that gate, because length and containment over JSON text survive where the path-access family does not. The per-operation narrowing that used to travel with the table (`ilike` on a string, `unnest` / `json_table` / `json_equal` on JSON) is not part of the protocol, and each of those facts is already owned by a probe that answers it: `supports_ilike()`, `supports_json_table()` and the JSON mixin's own version gates. `uuid.UUID` is `UUIDColumn` on every version, including those below 10.7 where MariaDB has no native `UUID` type — the native type is a storage fact and does not change what a UUID value can do.
