`suggested_data_types()` now answers what MariaDB actually stores rather than what it renders. `uuid` and `enum` are gone from the substitution table: MariaDB has had a native `UUID` column type since 10.7, and it renders `ENUM(...)` natively, and a name that appears in both sets means one of the two is a lie. The old `uuid` entry pointed at a 16-byte `BINARY`, which was true before 10.7 and false after it, so it would have quietly produced a column that is not a UUID on every supported server.

`real` joins the table with the reason attached: MariaDB's `REAL` is a synonym whose resolution depends on a SQL mode this framework does not read, and `information_schema` never writes the word back -- every wired server reports a `REAL` column as `double` (`float` under `REAL_AS_FLOAT`), so the concept cannot round-trip. The substitute is `DoubleType`, the storage the default server builds, and `FloatType` is what to declare for 4-byte single precision; the new `substitute_advice()` carries that sentence into the caller's error. `binary` / `varbinary` now answer this backend's own width-carrying classes, because a `BLOB` here is unbounded and cannot stand in for a width-constrained one; `array` answers `JsonType`, which is what a MariaDB array is actually made of; `interval` answers `VarCharType`, the character form MariaDB's own interval arithmetic produces, `INTERVAL` being an expression keyword here and never a column type; and `xml` is the one version-dependent entry -- `TextType` before 12.3, where MariaDB had no XML type at all, and `MariaDBXmlType` from 12.3, where it does.

The `UUID` (10.7) and `XMLTYPE` (12.3) version boundaries are added, both verified against live servers rather than read off a manual. `TRUNC` is re-gated to 12.2: it had been recorded as available in every version, and the scenario matrix says otherwise -- measured on fifteen wired servers, 10.2.44 through 13.1.1, it is absent on 10.2 through 12.1 and present on 12.2, 12.3, 13.0 and 13.1.
